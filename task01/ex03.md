# Exercise 3 - Overflow and Safe Arithmetic

## Part 1 - Predictions and Actual Results

The original array is:

```python
x = np.array([100, 200, 250], dtype=np.uint8)
```

| Expression | My prediction | Actual result |
|---|---|---|
| `x + 10` | `[110, 210, 4]` | `[110, 210, 4]` |
| `x + 100` | `[200, 44, 94]` | `[200, 44, 94]` |
| `x - 150` | `[206, 50, 100]` | `[206, 50, 100]` |
| `x * 2` | `[200, 144, 244]` | `[200, 144, 244]` |
| `x.astype(np.int16) + 100` | `[200, 300, 350]` | `[200, 300, 350]` |
| `x * 1.5` | `[150, 44, 119]` | `[150., 300., 375.]` |
| `(x * 1.5).dtype` | `uint8` | `float64` |

### Explanation of My Mistakes

I expected `x * 1.5` to overflow like arithmetic with integer values in a `uint8` array. I also predicted that its data type would remain `uint8`, because the numerical results are whole numbers. However, multiplying this array by the floating-point value `1.5` produces a `float64` array. Therefore, the results are `[150., 300., 375.]` and do not overflow at 255. I learned that the result's data type depends on the types used in the operation, not only on whether the resulting values have fractional parts.

## Part 2 - Adding 300

Running `print(x + 300)` produced:

```text
OverflowError: Python integer 300 out of bounds for uint8
```

The integer `300` itself is outside the valid range of `uint8` (0 to 255). In my NumPy environment, this raises an `OverflowError` instead of automatically converting the array to a larger integer type. I commented out this line in `ex03.py` so the rest of the program can run.

## Part 3 - Safe Addition

I implemented `add_safe(x, b)` without loops. It first converts the array to a wider integer type, adds `b`, clips the result to the range 0–255, and converts it back to `uint8`.

Test results for `x = [100, 200, 250]`:

```text
Safe +100: [200 255 255]
Safe -150: [  0  50 100]
```

When adding 100, results above 255 are limited to 255 instead of wrapping around. When subtracting 150, negative results are limited to 0. The returned array has data type `uint8`.

## Part 4 - Why Clipping After Addition Is Not Enough

`np.clip(x + 100, 0, 255)` is not safe because `x + 100` is calculated first, while `x` is still `uint8`. For example, `250 + 100` wraps around to `94`. Since `94` is already between 0 and 255, `np.clip` leaves it unchanged. To prevent this, I must convert to a wider integer type **before** adding, then clip the result, and finally convert back to `uint8`.

## Bonus - `int8` Overflow
